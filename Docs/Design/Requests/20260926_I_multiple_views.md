# 요청: 한 렌더러에서 여러 뷰, 뷰마다 시간 이력 (I 트랙, 2026-09-26, M0)

## 왜 필요한가

사용자 결정으로 첫 목표는 M0 "게임 개발 시작 최소선"이다(재구축 계획 14.5). 완료 조건 가운데 하나가 "편집기 씬 뷰와 플레이 모드가 새 렌더러로 그려진다"이다. Unity 편집기에서는 한 프레임에 여러 카메라가 그려진다.
- 씬 뷰 카메라와 Game 뷰 카메라. 둘 다 열려 있으면 플레이 중 매 프레임 둘 다 그려진다.
- 렌더 텍스처 카메라. 미니맵, 거울 카메라, 게임 안 모니터, 분할 화면처럼 게임이 쓰는 것이다(M0 뒤 기능 목록 9번).

지금 `FrameContext`에는 `mainView` 하나만 있다. 시간 상태(INTERFACES 5.5.2 표)가 렌더러 하나에 하나씩이다.
- 반사 거리 이력(16.6 MB), 화면 프로브, 시점 VSM 페이지, R 프록시 절단 이력, 이전 뷰 행렬.
- 그래서 호스트가 한 Unity 프레임에 두 카메라의 프레임을 번갈아 넣으면 두 뷰의 이력이 섞인다(재투영이 다른 카메라의 이력을 읽는다).
- 호스트가 할 수 있는 정확한 우회는 "뷰가 바뀔 때마다 Cut"뿐이다. 두 뷰가 번갈아 그려지는 동안에는 뷰별 이력이 매 프레임 초기화된다. 틀리지는 않지만 매 프레임 잡음 최대 상태다. 품질 결함이다.
- 렌더러를 뷰마다 하나씩 만드는 것은 GpuScene, GI 월드 캐시(4K 138.8~198 MB), BLAS, 클러스터를 복제하게 된다.

## 요청

1. **뷰 키**: `FrameContext`(또는 `ViewDesc`)에 호스트가 정하는 `viewId`(uint32)를 둔다. 같은 키의 프레임끼리만 이력을 잇는다.
2. **뷰별 상태**: 5.5.2 표에서 "Cut: 버림"인 항목을 뷰 키별 저장소로 옮긴다. 반사·화면 프로브, 시점 VSM, 프록시 절단, 이전 뷰 행렬이 그것이다.
   - 처음 보는 키는 새로 만든다(첫 프레임 = Cut과 같다).
   - N 프레임 동안 안 쓰인 키는 해제한다. 해제 규칙과 메모리 상한은 core가 정한다.
   - "Cut: 유지"인 세계 공간 캐시(R GI 캐시), GpuScene, 대기 표는 모든 뷰가 함께 쓴다.
3. **한 Unity 프레임에 여러 뷰**: 호스트는 카메라마다 프레임 패킷을 따로 큐에 넣는다(지금처럼, 뷰 키만 붙인다).
   - GPU 시뮬레이션(C0), 장면 갱신(변환·포즈)은 그 Unity 프레임의 첫 뷰에서 한 번만 적용해야 한다. 뷰마다 적용하면 두 번째 뷰가 움직임 0이 된다.
   - 그래서 패킷에 "같은 시뮬레이션 프레임의 추가 뷰" 표시(`sceneFrame` 번호 같은 것)가 필요하다. 형태는 core가 정한다.
4. **비용 표기**: 뷰 하나를 더할 때의 GPU 시간은 뷰 해상도에 비례하는 항들이다. 세계 공간 갱신(GI 캐시 갱신, VSM 태양 페이지의 세계 부분)은 뷰마다 반복하지 않는다. 설계 합계표(2.13)에 뷰 추가 비용식이 필요하다.

## 호스트 쪽(I)

- ABI: `UnxFrameDesc`에 `viewId`를 둔다(version 2).
- 브리지: Unity 카메라마다 안정된 키를 만든다(씬 뷰, Game 뷰, 각 렌더 텍스처 카메라). 한 Unity 프레임의 첫 카메라가 장면 갱신을 싣는다.
- 받기 전까지의 임시 경로: 씬 뷰 카메라도 그린다. 그리는 뷰가 바뀌면 Cut을 넣는다. 편집 모드에서는 보통 씬 뷰만 다시 그려지므로 번갈아 그려지는 일이 드물다. 플레이 중 두 뷰가 다 열려 있으면 위의 품질 결함이 생기고, 상태 문서에 그렇게 적는다.
