# 제안: 커널(DXIL) 내용 주소 캐시 (인프라 → 코어, 2026-09-26)

빌드 가속(REBUILD_PLAN 14.3 ⑭) 과정에서 나온 제안이다. `Tools/ShaderCompiler`는 코어 소유라서, 코어가 적용하거나 인프라에 위임한다.

## 1. 측정 [실측]

- 기준 빌드: 워크트리 84e7c8b, 모든 트랙, `-Jobs 4`. 각 출력의 첫 빌드 시간을 합하면 750 s다.
  - C++ obj: 366 s (48.8 %)
  - 커널 `.dxil` 207개: 236 s (31.5 %)
  - C++20 모듈 스캔과 수집: 103 s (13.7 %). 스캔은 끈다(`20260926_Infra_build_acceleration.md`).
  - 링크: 19 s
- PCH, unity 빌드, C++ 컴파일러 캐시는 C++ 쪽에만 듣는다. 커널 31.5 %에는 효과가 없다.
- 두 빌드(기준, 모든 가속 옵션)의 DXIL 207개는 바이트 단위로 같았다. 커널 출력은 호스트 C++ 빌드 옵션과 무관하다.
- 커널 재컴파일은 빌드 폴더마다 따로 일어난다.
  - 최근 24시간에 활성 빌드 폴더 27개가 obj를 2,236개 이상 다시 만들었다(파일 시각 기준 하한).
  - 공용 `.hlsli`를 건드리면 폴더마다 다시 컴파일한다. `Bindless.hlsli` 205 커널, `Frame.hlsli` 147 커널, `Scene.hlsli` 114 커널이 여기에 걸린다(HeaderCost).

## 2. 제안

`unx_shaderc`에 내용 주소 캐시를 넣는다(ccache의 direct mode와 같은 구조).
- **키** = SHA-256(다음 전부):
  - DXC 버전(`dxcompiler.dll`과 `dxil.dll`의 해시)
  - `unx_shaderc` 자신의 캐시 형식 버전
  - profile, entry, `-D` 목록, `--max-kb`
  - 원본 파일 내용
- **manifest**: 키마다 지난 컴파일이 연 include 파일 목록과 각 내용의 SHA-256을 둔다. `RecordingIncludeHandler`가 이미 이 목록을 모은다.
  - 모든 include의 현재 해시가 manifest와 같으면 캐시된 DXIL, PDB, depfile을 복사하고 DXC를 부르지 않는다.
  - 하나라도 다르면 컴파일하고 새 항목을 더한다.
  - include 경로 순서가 바뀌면 같은 이름이 다른 파일로 풀릴 수 있다. 그래서 `-I` 목록도 키에 넣는다.
- **위치**: 폴더와 워크트리가 같이 쓰는 한 곳이다(예: `%LOCALAPPDATA%\UnravelNext\ShaderCache`). 쓰기는 임시 파일에 쓴 뒤 원자적 이름 바꾸기로 한다. 여러 폴더가 동시에 빌드해도 안전하다.
- **정확성**: 키에 없는 입력(환경, 시계)은 DXC 출력에 영향이 없다. 그래도 도입할 때 한 번은 캐시를 켠 빌드와 끈 빌드의 DXIL을 모두 비교해 같음을 보인다. `--no-cache` 스위치와 크기 상한(오래된 것부터 지움)을 둔다.
- depfile은 캐시 항목에서 그대로 복사하되, 그 폴더의 경로가 들어간 줄만 현재 출력 경로로 다시 쓴다.

## 3. 예상 효과 [예상]

- 같은 `.hlsli` 수정 뒤 두 번째 이후 폴더: 커널 컴파일은 해시와 복사만 남는다(커널당 수 ms). 첫 폴더는 지금과 같다.
- 주석만 바꾼 수정이라도 파일 내용이 달라지므로 적중하지 않는다. 전처리 결과를 키로 쓰면 적중하지만, 전처리 비용이 든다. 먼저 direct mode로 하고, 적중률을 잰 뒤 정한다.
- 새로 만든 빌드 폴더, `-Committed` 게이트 빌드, 트랙 집합이 바뀌어 폴더를 지운 경우: 이미 누군가 컴파일한 커널은 모두 적중한다. 전체 빌드 750 s 가운데 236 s에 해당한다(-j4 기준).

## 4. 요청

코어가 직접 적용하거나, 이 작업에 한해 `Tools/ShaderCompiler`를 인프라에 위임해 달라. 위임하면 인프라가 구현하고, 캐시를 켠 빌드와 끈 빌드의 DXIL이 같은지와 폴더 간 시간을 [실측]으로 붙인다.
