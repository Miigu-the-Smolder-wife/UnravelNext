# 렌더러 재설계 지시서 (2026-09-29, 1440p 2~3 ms)

이 문서는 설계를 맡을 세션이나 도구에 주는 지시서다. 설계 결과를 가져오면 조정 세션이 아래 "평가 기준"으로 판정한 뒤 구현에 넣는다. 저장소는 `github.com/Miigu-the-Smolder-wife/UnravelNext`(main)이다.

## 1. 목표 (사용자 결정)

- **1440p 출력에서 렌더러 GPU 프레임 2~3 ms.** 1080p는 그 이하이고, 4K는 최대 품질 목표로서 6.06 ms(165 fps)다.
- GPU 시뮬레이션(유체 128k 입자 약 0.63 ms/프레임, 파티클, 천)은 별도 항목이다. 렌더러와 합친 전체 프레임도 6.06 ms 안에 들어야 한다.
- 개발 PC는 RTX 4080(드라이버 591.86)과 i9-13900KF다. 완성된 게임은 일반 PC에서도 돌아야 한다(아래 5절).

## 2. 품질 규칙 (바꿀 수 없음)

- 품질, 표본 수, 부하(장면 밀도, 광원 수, 입자 수)를 낮춰서 성능을 만들지 않는다. 비용이 부하에 비례하면 부하를 변수로 둔 공식으로 쓰고, 맞지 않으면 그 경로를 다시 설계한다. 부하를 줄이는 것은 선택지에도 넣지 않는다.
- 추정 방식을 바꾸는 레버의 기준은 사용자가 정했다. **"보이는 것이 같으면 된다. 게임플레이 중 다양한 행동에서도."** 정지 화면과 움직임(카메라 회전, 걷기, 물체가 움직임, 빛 변화) 모두에서 원래 해상도·원래 추정과 눈으로 구분되지 않아야 한다.
- 승인된 레버는 두 가지다.
  - 내부 해상도 + 시간 업스케일. 단, 원래 해상도와 같아 보여야 한다. 현재 구현은 확연히 흐려서 불합격이다(`Results/Local/Verify974c6bb/`).
  - 화면 GI 조회의 프레임 분할. 이득이 없어 지금은 꺼져 있다.
- 그 밖에 계산량을 바꾸는 레버(광선 수, GI 광선 예산 등)는 사용자 결정 사항이다. 설계에 넣으려면 "결정 필요"로 따로 표시하고, 기준을 만족한다는 근거를 붙인다.
- 모든 수치에 [실측] 또는 [예상]을 붙인다. 비용은 FLOP가 아니라 실제 접근 패턴의 지연·대역폭·단편 수로 계산하고, 실측 하한(`Tools/Microbench/Results/FLOORS.md`, 없으면 microbench로 새로 잰다)에 근거한다. "정확"하다는 주장에는 성립 조건을 적는다.
- 회피성 구현(특정 장면·카메라에서만 싸지는 지름길, 결과를 숨기는 후처리)은 금지다. 캐시는 최악의 경우(카메라와 해가 빠르게 움직이고, 기차가 달리는 중)에도 예산 안이어야 한다. 해 속도는 무제한이라 모든 그림자 페이지를 매 프레임 다시 그려도 맞아야 한다.
- Unreal Engine 소스는 개념 참고용으로만 쓴다(EULA). 코드는 한 줄도 복사하지 않고, 참고한 개념과 파일 경로만 적는다.

## 4. 다시 설계할 것

1440p 2~3 ms는 지금(9.6~11 ms)의 약 1/4이다. 아래 영역은 **방식부터 다시 정한다.** 각 영역이 표현하는 정보량부터 따지고(예: 이 화면에서 반사가 실제로 담는 정보는 몇 표본 분량인가), 그 정보를 가장 싸게 얻는 표현과 계산을 고른다.

1. **반사.** 지금 방식:
   - M(거칠기 < 0.14: 화소당 광선 1개), G(흐림 < 3 px: 화소당 4개), K(캐시 방사휘도)로 나눈다.
   - hit마다 전체 재질, GI 캐시, 국소광 표본 + 그림자 광선, 해 VSM을 셰이딩한다.
   - 평면 거울은 래스터 보조 뷰로 그린다.

   hit 셰이딩(1.69 ms)이 최대 항이다.
2. **GI.** 지금 방식:
   - 월드 공간 방사휘도 캐시: 해시 격자 20만 항목, 항목마다 SH + 조도 지도, 프레임당 광선 50만.
   - 화면 프로브(8 px 간격).
   - 화소마다 레벨별 8모서리 삼선형 조회(r.gi.screen), 12탭 쌍방 필터.

   벽 너머 누출 약 3%가 남아 있다. 막으려던 앵커 가시성은 얼룩을 만들어 꺼 두었다.
3. **그림자 필터.**
   - 해: 반그림자 추정기(차단물 탐색 5탭 + 필터 16탭).
   - 국소광: 큐브 VSM 페이지, froxel 목록, 셋째 광원부터 overflow 목록.

   광원이 많은 욕탕에서 비용이 크다.
4. **공기 froxel 적분**과 국소광 페이지 표시(localmark).
5. **셰이딩·해석.** 가시성 버퍼 기반 타일 셰이딩, 면광원은 LTC다.
6. **업스케일 재구성**(쓸 경우). 정지 화면에서는 원래 해상도 디테일까지 수렴해야 하고, 움직임에서도 흐림·잔상·깜빡임이 원래 해상도와 구분되지 않아야 한다. 판정 지표도 설계에 포함한다. 예: 같은 출력 해상도에서 `--capture`(원래) 대 `--capture-output`(업스케일)의 고주파 에너지 비와 SSIM, 정지와 움직임 각각.
7. **프레임 고정비.** 패스 120~157개, 장벽 627~962개, 프레임과 패스 합의 차 0.6~0.7 ms. 패스 병합, 장벽 일괄 처리, 비동기 계산을 다룬다. 비동기 겹침은 이전에 2~6%만 실측됐으니, 쓰려면 새로 재서 근거를 댄다.

다시 설계하지 않는 것도 적는다. 장면 표현, 가시성 버퍼, VSM 페이징 구조, 재질 체계, 렌더 그래프, 시험 도구, Unity 연결은 유지하는 것이 기본이다. 바꿔야 한다면 이유와 비용을 적는다.

## 5. 제약

- **이식성.** 표준 D3D12만 쓴다(DX12 Ultimate급, 기능 수준 12_0 이상, 표준 셰이더 모델, DXR 1.1 인라인 광선 질의 가능). 핵심 경로에 벤더 전용 기능(NVAPI SER/OMM 등)을 쓰지 않는다. 필요한 하드웨어를 명시한다.
- **메모리.** 일반 PC(RAM 16 GB, VRAM 8 GB) 기준이다. NVMe → RAM 캐시 → VRAM 3단 상주를 쓰고, 쓰기 전에 데이터가 상주해 있어야 한다(저해상도 대체 금지).
- **게임 조건.**
  - 1인칭, 움직이는 물리 물체 최대 약 1000개, 파괴 파편, 유체 128k.
  - 폭발 섬광 같은 동적 광원.
  - 달리는 기차(차량 좌표계, 창밖이 빠르게 지나감).
  - 해 속도 무제한.
  - 실내가 주요 장면이다(욕탕, 기차).
- **4K 최대 품질 목표(6.06 ms)와 RPP-1 부하 정의**는 그대로다. 이번 목표는 1440p 2~3 ms를 추가로 만족하는 것이다.
- **DXIL 크기 한도**(커널당 약 200 KB)와 구조적 디스패치 상한(데이터 분포와 무관하게 디스패치 하나의 최악 시간이 유한해야 함)을 지킨다.

## 6. 설계 결과물 (이 형식으로 가져온다)

1. **영역별 절** (4절의 1~7).
   - 정보량 분석, 새 표현·알고리즘, 필요한 자료 구조와 메모리.
   - 비용 공식: 해상도·부하를 변수로 쓰고, 1080p·1440p·4K와 두 장면의 값을 대입한다. 근거가 되는 실측 하한도 적는다.
   - 품질 정의와 검증 방법: 기준 경로 추적 대비 편향과 잡음, furnace 같은 분석 시험, 움직임 시험, 눈으로 보는 판정 장면.
   - 실패 모드와 최악의 경우 비용.
2. **전체 예산표.** 1440p에서 2~3 ms 안의 영역별 할당과 여유. 1080p와 4K 열도 함께 둔다. 고정비(그래프, 장벽, 후처리, 업스케일)도 포함한다.
3. **결정 필요 항목.** 사용자가 정해야 하는 레버를 따로 모으고, 각각의 이득 [예상]과 "보이는 것이 같다"의 근거를 붙인다.
4. **구현 순서.** 각 단계가 끝날 때 렌더러가 동작하고 시험이 통과하는 순서로 쓴다. 단계마다 교체되는 파일·모듈, 기대 이득 [예상], 로컬 확인 항목을 적는다.
5. **새로 재야 할 microbench 목록.** 하한이 없는 접근 패턴이 대상이다.

## 7. 평가 기준 (조정 세션이 판정)

- 비용 공식이 실측 하한과 실제 접근 패턴에 맞는가. FLOP만으로 셈하지 않았는가.
- 1440p 합계가 여유를 두고 3 ms 안인가. 1080p와 4K도 맞는가.
- 품질·표본·부하를 몰래 낮추지 않았는가. 해상도, 지연 프레임, 광선 수, 누적 길이 모두 해당한다.
- 캐시와 재사용이 최악의 경우(빠른 카메라, 해, 기차)에도 예산 안인가.
- 이식성, 메모리, DXIL, 디스패치 상한 제약을 지키는가.
- 품질 정의가 측정할 수 있는 형태이고, 기존 시험을 통과하는가. 기존 시험: reflectionanalytic, gianalytic, hostmotion, vsmtests, localshadowtests, shadingtests, volumetests.
- 구현 순서가 단계마다 동작하는 렌더러를 남기는가.
